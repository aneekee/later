# SQL queries by user action: after indexes

This file lists the same operations as [2026091301\_\_baseline.md](./2026091301__baseline.md), re-measured after adding indexes. Each operation includes the exact SQL generated by Prisma, ready to run in DBeaver or psql with `EXPLAIN (ANALYZE, BUFFERS)`, and compares timings with the baseline.

The SQL was captured from the Prisma query log (see `src/prisma/prisma.service.ts`) during a manual session on the same seeded local data. Timings are measured by Prisma, so they include driver and network overhead, not only execution time in Postgres. Confirm each improvement with `EXPLAIN (ANALYZE, BUFFERS)`.

> ⚠️ `EXPLAIN ANALYZE` actually executes the statement. Write operations are wrapped in `BEGIN … ROLLBACK` so they leave no data behind.

## What changed

Migration `prisma/migrations/20260913214750_update_note_tables_indexes`:

```sql

CREATE INDEX "messages_chat_id_created_at_idx" ON "messages"("chat_id", "created_at");
```

No application code changed. The generated SQL is identical to the baseline.

## 2. List chats

`GET /v1/chats` → `ChatsService.listChats`. Two queries in one transaction.

| Query     | Baseline    | After indexes                      | Expected index                                                                    |
| --------- | ----------- | ---------------------------------- | --------------------------------------------------------------------------------- |
| 2a. Page  | ~220–260 ms | ~1.4–3.6 ms (one sample at 8.8 ms) | `chats_user_id_idx`, plus `messages_chat_id_created_at_idx` for `MAX(created_at)` |
| 2b. Count | ~3–5 ms     | ~0.8–1.7 ms                        | `chats_user_id_idx`                                                               |

Before the indexes, the `MAX(created_at)` subquery scanned `messages` once per chat. Now each lookup reads a single entry from the end of `messages_chat_id_created_at_idx`. The query still runs one subquery per chat of the user, so its cost grows with the number of chats. Storing `last_message_at` on `chats` (the TODO in `chats.service.ts`) would remove that.

```sql
-- 2a. Page
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, user_id AS "userId", title, created_at AS "createdAt" FROM chats
WHERE user_id = '9238aa00-e31f-42e3-b0fd-25274f164029'
ORDER BY (
  SELECT MAX(created_at) FROM messages WHERE chat_id = chats.id
) DESC NULLS LAST
LIMIT 20 OFFSET 0;

-- 2b. Total count
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) AS "_count$_all" FROM (
  SELECT "public"."chats"."id" FROM "public"."chats"
  WHERE "public"."chats"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029'
  OFFSET '0'
) AS "sub";
```

Expected plan: `Index Scan using chats_user_id_idx on chats`, with a `SubPlan` made of `Limit → Index Only Scan Backward using messages_chat_id_created_at_idx on messages` with `loops` equal to the number of chats. There should be no `Seq Scan on messages`.

## 4. List messages in a chat (unresolved filter)

`GET /v1/chats/:chatId/messages?resolution=unresolved` → `MessagesService.listMessages`. After the access check, it runs four queries: the page, one per `include` relation (`textMessage`, `messageResolution`), and the count.

| Query                          | Baseline   | After indexes                            | Expected index                                   |
| ------------------------------ | ---------- | ---------------------------------------- | ------------------------------------------------ |
| 4a. Page                       | ~70–125 ms | ~1.3–2.6 ms (one sample at 21.5 ms)      | `messages_chat_id_created_at_idx`                |
| 4b. include: textMessage       | ~1–4 ms    | ~0.7–4.8 ms                              | `text_messages_message_id_key` (unchanged)       |
| 4c. include: messageResolution | ~1–5 ms    | ~1.6–7.6 ms                              | `message_resolutions_message_id_key` (unchanged) |
| 4d. Count                      | ~46–86 ms  | ~1.2–3.8 ms (samples at 8.1 and 30.8 ms) | `messages_chat_id_created_at_idx`                |

4a and 4d are the queries that changed. 4b and 4c were already using unique-key indexes, and their spread is noise. The outliers (21.5 ms for 4a, 8.1 ms for 4d) happened when a chat list request was running at the same time. In the log, their queries are interleaved.

## 9. List resolved messages (all chats of the user)

`GET /v1/chats/:chatId/messages/resolved` → `MessagesService.listResolvedMessages`. This is the only operation that `message_resolutions_created_at_idx` was added for. It was captured in a follow-up session, right after resolving two more messages, so the user had 6 resolved messages instead of 2.

The route sits under `:chatId`, but the service ignores it: it lists resolved messages across **all** of the user's chats, ordered by resolution date. It doesn't call `checkAccess`. It runs five queries in one transaction: the page, one per `include` relation (`textMessage`, `messageResolution`, `chat`), and the count.

| Query                          | Baseline | After indexes |
| ------------------------------ | -------- | ------------- |
| 9a. Page                       | ~127 ms  | ~5.7 ms       |
| 9b. include: textMessage       | ~2 ms    | ~3.7 ms       |
| 9c. include: messageResolution | ~2.5 ms  | ~6.2 ms       |
| 9d. include: chat              | ~3 ms    | ~9.2 ms       |
| 9e. Count                      | ~68 ms   | ~2.9 ms       |
| **Total**                      | ~203 ms  | ~28 ms        |

9a and 9e improved ~20×. There's one sample in each session, so treat the numbers as rough. 9b–9d are primary-key or unique-key lookups that weren't affected by the new indexes. They look slower only because of single-sample noise and because they now fetch 6 rows instead of 2. In 9d, Prisma sent the same chat ID 6 times.

The timings alone don't show which plan 9a uses. The drop from ~127 ms to ~6 ms matches the plan that starts from `chats_user_id_idx`. Run `EXPLAIN` to confirm whether `message_resolutions_created_at_idx` is used at all.

```sql

EXPLAIN (ANALYZE, BUFFERS)

FROM "public"."messages"
LEFT JOIN "public"."message_resolutions" AS "orderby_1" ON ("orderby_1"."message_id") = ("public"."messages"."id")
LEFT JOIN "public"."chats" AS "j0" ON ("j0"."id") = ("public"."messages"."chat_id")
LEFT JOIN "public"."message_resolutions" AS "j1" ON ("j1"."message_id") = ("public"."messages"."id")
WHERE (("j0"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029' AND ("j0"."id" IS NOT NULL))
   AND (NOT ("j1"."message_id" IS NULL)))
ORDER BY "orderby_1"."created_at" DESC
LIMIT '20' OFFSET '0';

-- 9b. include: textMessage
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."text_messages"."id", "public"."text_messages"."message_id", "public"."text_messages"."content"
FROM "public"."text_messages"
WHERE "public"."text_messages"."message_id" IN ('f26f6669-239b-4510-b944-30232b6ac41f','7311d887-6624-4e0f-91b0-19ec7fa17b18','d203caa8-a685-41b1-8633-82b7d1dd5ef5','02363197-dd7f-4d15-bd6d-9f51bdf7f3f1','860e6ad7-b77e-4878-bcc5-3f0cdef02899','f4f2a25b-ab22-43af-8162-2e3d422402ab')
OFFSET '0';

-- 9c. include: messageResolution
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."message_resolutions"."id", "public"."message_resolutions"."message_id", "public"."message_resolutions"."note", "public"."message_resolutions"."created_at"
FROM "public"."message_resolutions"
WHERE "public"."message_resolutions"."message_id" IN ('f26f6669-239b-4510-b944-30232b6ac41f','7311d887-6624-4e0f-91b0-19ec7fa17b18','d203caa8-a685-41b1-8633-82b7d1dd5ef5','02363197-dd7f-4d15-bd6d-9f51bdf7f3f1','860e6ad7-b77e-4878-bcc5-3f0cdef02899','f4f2a25b-ab22-43af-8162-2e3d422402ab')

WHERE "public"."chats"."id" IN ('d7766486-c374-4c9a-b137-0935036b3c54','d7766486-c374-4c9a-b137-0935036b3c54','d7766486-c374-4c9a-b137-0935036b3c54','d7766486-c374-4c9a-b137-0935036b3c54','d7766486-c374-4c9a-b137-0935036b3c54','d7766486-c374-4c9a-b137-0935036b3c54')

  WHERE (("j0"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029' AND ("j0"."id" IS NOT NULL))
     AND (NOT ("j1"."message_id" IS NULL)))
  OFFSET '0'
```

What to look for in 9a and 9e:

- **Which index the planner starts from.** It can start from the user's chats (`chats_user_id_idx`), go to `messages` by `chat_id`, then join `message_resolutions` by `message_id`, and sort the result. Or it can walk `message_resolutions_created_at_idx` backwards and drop rows that belong to other users until it has 20. The second only pays off when the user owns a large share of all resolutions. For a typical user it reads many rows of other users.
- **If `message_resolutions_created_at_idx` is never used** by 9a, drop it. It costs write time on every resolve and gives nothing back.
- **The Sort node.** With the first plan, expect a `Sort` (ideally `top-N heapsort`) over all of the user's resolved messages.

## Observations

- **The indexes fixed all three slow screens.** List chats went from ~230 ms to ~2 ms, list messages from ~130–200 ms to ~7–15 ms in total, and list resolved messages from ~200 ms to ~28 ms. After the indexes, no captured query is consistently above ~10 ms.
- **The write paths didn't get measurably slower.** Inserts and deletes stay at a few ms even though they now maintain the extra indexes.
- **The planner may not use `message_resolutions_created_at_idx`.** The speedup of 9a and 9e is explained by `chats_user_id_idx` and `messages_chat_id_created_at_idx` alone. Run 9a with `EXPLAIN (ANALYZE, BUFFERS)`. If the plan doesn't mention `message_resolutions_created_at_idx`, drop it in a follow-up migration.
- **Outliers come from concurrent requests.** The samples at 8–31 ms appear where the chat list and message list requests overlap in the log. Take the median of several runs rather than a single sample.
- **Growth risks remain.** 2a still runs one `MAX(created_at)` lookup per chat, and 4d and 9e still count every matching row on each page request. They're fast at this data size but grow linearly: with the number of chats for 2a, and with chat size or resolved message count for 4d and 9e. Storing `last_message_at` on `chats`, cursor pagination, and dropping or caching `totalSize` would address these if they become slow again.
