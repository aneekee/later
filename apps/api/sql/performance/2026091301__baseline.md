# SQL queries by user action

This file lists the unique database operations the app performs, mapped to the endpoints that trigger them. Each operation includes the exact SQL generated by Prisma, ready to run in DBeaver or psql with `EXPLAIN (ANALYZE, BUFFERS)`.

The SQL was captured from the Prisma query log (see `src/prisma/prisma.service.ts`) during a manual session on seeded local data. Timings are from that session and serve as a baseline for comparison.

> ⚠️ `EXPLAIN ANALYZE` actually executes the statement. Write operations are wrapped in `BEGIN … ROLLBACK` so they leave no data behind.

IDs used in the examples (replace with IDs from your own database):

## 1. Load current user

`GET /v1/auth/me` and `POST /v1/auth/refresh` both call `UsersService.findById` and produce identical SQL.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."users"."id", "public"."users"."username", "public"."users"."password", "public"."users"."is_verified", "public"."users"."created_at"
FROM "public"."users"
WHERE ("public"."users"."id" = '9238aa00-e31f-42e3-b0fd-25274f164029' AND 1=1)
LIMIT '1' OFFSET '0';
```

## 2. List chats

`GET /v1/chats` → `ChatsService.listChats`. Two queries in one transaction.

```sql
-- 2a. Page (~220–260 ms, the slowest query in the app)
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, user_id AS "userId", title, created_at AS "createdAt" FROM chats
WHERE user_id = '9238aa00-e31f-42e3-b0fd-25274f164029'
ORDER BY (
  SELECT MAX(created_at) FROM messages WHERE chat_id = chats.id
) DESC NULLS LAST
LIMIT 20 OFFSET 0;

-- 2b. Total count (~3–5 ms)
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) AS "_count$_all" FROM (
  SELECT "public"."chats"."id" FROM "public"."chats"
  WHERE "public"."chats"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029'
  OFFSET '0'
) AS "sub";
```

## 3. Check chat access

`ChatsService.checkAccess` is not an endpoint. It runs first in every `/v1/chats/:chatId/messages/*` request.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."chats"."id", "public"."chats"."user_id", "public"."chats"."title", "public"."chats"."created_at"
FROM "public"."chats"
WHERE ("public"."chats"."id" = 'd7766486-c374-4c9a-b137-0935036b3c54'
   AND "public"."chats"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029')
LIMIT '1' OFFSET '0';
```

## 4. List messages in a chat (unresolved filter)

`GET /v1/chats/:chatId/messages?resolution=unresolved` → `MessagesService.listMessages`. After the access check, it runs four queries: the page, one per `include` relation (`textMessage`, `messageResolution`), and the count.

```sql
-- 4a. Page (~70–125 ms)
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."messages"."id", "public"."messages"."type"::text, "public"."messages"."chat_id", "public"."messages"."created_at"
FROM "public"."messages"
LEFT JOIN "public"."message_resolutions" AS "j0" ON ("j0"."message_id") = ("public"."messages"."id")
WHERE ("public"."messages"."chat_id" = 'd7766486-c374-4c9a-b137-0935036b3c54' AND ("j0"."message_id" IS NULL))
ORDER BY "public"."messages"."created_at" DESC
LIMIT '20' OFFSET '0';

-- 4b. include: textMessage (~1–4 ms)
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."text_messages"."id", "public"."text_messages"."message_id", "public"."text_messages"."content"
FROM "public"."text_messages"
WHERE "public"."text_messages"."message_id" IN ('311538f3-340d-4c55-8454-9c4cd454d7c6','427a73ca-1c25-4970-a3f9-c19c32e23fc5','1d65c541-d1a3-4564-afc5-6db6c469dc97','b40ae7f6-a752-4e40-acc1-84fa1c79bb78','dcd6569d-8076-4d2f-94f9-a69442201dcd')
OFFSET '0';

-- 4c. include: messageResolution (~1–5 ms)
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."message_resolutions"."id", "public"."message_resolutions"."message_id", "public"."message_resolutions"."note", "public"."message_resolutions"."created_at"
FROM "public"."message_resolutions"
WHERE "public"."message_resolutions"."message_id" IN ('311538f3-340d-4c55-8454-9c4cd454d7c6','427a73ca-1c25-4970-a3f9-c19c32e23fc5','1d65c541-d1a3-4564-afc5-6db6c469dc97','b40ae7f6-a752-4e40-acc1-84fa1c79bb78','dcd6569d-8076-4d2f-94f9-a69442201dcd')
OFFSET '0';

-- 4d. Total count (~50–80 ms)
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) AS "_count$_all" FROM (
  SELECT "public"."messages"."id" FROM "public"."messages"
  LEFT JOIN "public"."message_resolutions" AS "j0" ON ("j0"."message_id") = ("public"."messages"."id")
  WHERE ("public"."messages"."chat_id" = 'd7766486-c374-4c9a-b137-0935036b3c54' AND ("j0"."message_id" IS NULL))
  OFFSET '0'
) AS "sub";
```

For an empty chat, 4b and 4c become `IN (NULL)`. That's harmless and not worth testing.

## 5. Create text message

`POST /v1/chats/:chatId/messages/text` → `MessagesService.createTextMessage`. After the access check, it runs five queries: Prisma inserts the rows, then re-reads the message with its `include` in three SELECTs by primary or unique key.

```sql
BEGIN;

EXPLAIN (ANALYZE, BUFFERS)
INSERT INTO "public"."messages" ("id","type","chat_id","created_at")
VALUES ('00000000-0000-0000-0000-000000000001', CAST('TEXT'::text AS "public"."message_type"), 'd7766486-c374-4c9a-b137-0935036b3c54', now())
RETURNING "public"."messages"."id";

EXPLAIN (ANALYZE, BUFFERS)
INSERT INTO "public"."text_messages" ("id","message_id","content")
VALUES ('00000000-0000-0000-0000-000000000002', '00000000-0000-0000-0000-000000000001', 'test')
RETURNING "public"."text_messages"."id";

EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."messages"."id", "public"."messages"."type"::text, "public"."messages"."chat_id", "public"."messages"."created_at"
FROM "public"."messages" WHERE "public"."messages"."id" = '00000000-0000-0000-0000-000000000001' LIMIT '1' OFFSET '0';

EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."text_messages"."id", "public"."text_messages"."message_id", "public"."text_messages"."content"
FROM "public"."text_messages" WHERE "public"."text_messages"."message_id" = '00000000-0000-0000-0000-000000000001' OFFSET '0';

EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."message_resolutions"."id", "public"."message_resolutions"."message_id", "public"."message_resolutions"."note", "public"."message_resolutions"."created_at"
FROM "public"."message_resolutions" WHERE "public"."message_resolutions"."message_id" = '00000000-0000-0000-0000-000000000001' OFFSET '0';

ROLLBACK;
```

## 6. Delete message

`DELETE /v1/chats/:chatId/messages/:messageId` → `MessagesService.deleteMessage`. After the access check, it runs a single query. The related `text_messages` and `message_resolutions` rows are removed by DB-level `ON DELETE CASCADE`, so they don't appear in the Prisma log. Their cost shows up as `Trigger for constraint …` lines at the bottom of the plan.

```sql
BEGIN;
EXPLAIN (ANALYZE, BUFFERS)
DELETE FROM "public"."messages"
WHERE ("public"."messages"."id" = 'dcd6569d-8076-4d2f-94f9-a69442201dcd' AND 1=1)
RETURNING "public"."messages"."id", "public"."messages"."type"::text, "public"."messages"."chat_id", "public"."messages"."created_at";
ROLLBACK;
```

## 7. Resolve message

`PUT /v1/chats/:chatId/messages/:messageId/resolution` → `MessagesService.resolveMessage`. After the access check, it runs a single query. Without a note, the `note` column is omitted. The target message must not be resolved yet, otherwise the unique constraint on `message_id` fails.

## 9. List resolved messages (all chats of the user)

`GET /v1/chats/:chatId/messages/resolved` → `MessagesService.listResolvedMessages`. The route sits under `:chatId`, but the service ignores it: it lists resolved messages across **all** of the user's chats, ordered by resolution date. It doesn't call `checkAccess`. It runs five queries in one transaction: the page, one per `include` relation (`textMessage`, `messageResolution`, `chat`), and the count.

The `where` filters on relations, so Prisma turns them into `LEFT JOIN`s. Note that `message_resolutions` is joined **twice**: once as `orderby_1` for `orderBy: { messageResolution: { createdAt: 'desc' } }`, and once as `j1` for `messageResolution: { isNot: null }`.

```sql
-- 9a. Page (~127 ms)
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."messages"."id", "public"."messages"."type"::text, "public"."messages"."chat_id", "public"."messages"."created_at"
FROM "public"."messages"
LEFT JOIN "public"."message_resolutions" AS "orderby_1" ON ("orderby_1"."message_id") = ("public"."messages"."id")
LEFT JOIN "public"."chats" AS "j0" ON ("j0"."id") = ("public"."messages"."chat_id")
LEFT JOIN "public"."message_resolutions" AS "j1" ON ("j1"."message_id") = ("public"."messages"."id")
WHERE (("j0"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029' AND ("j0"."id" IS NOT NULL))
   AND (NOT ("j1"."message_id" IS NULL)))
ORDER BY "orderby_1"."created_at" DESC
LIMIT '20' OFFSET '0';

-- 9b. include: textMessage (~2 ms)
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."text_messages"."id", "public"."text_messages"."message_id", "public"."text_messages"."content"
FROM "public"."text_messages"
WHERE "public"."text_messages"."message_id" IN ('860e6ad7-b77e-4878-bcc5-3f0cdef02899','f4f2a25b-ab22-43af-8162-2e3d422402ab')
OFFSET '0';

-- 9c. include: messageResolution (~2.5 ms)
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."message_resolutions"."id", "public"."message_resolutions"."message_id", "public"."message_resolutions"."note", "public"."message_resolutions"."created_at"
FROM "public"."message_resolutions"
WHERE "public"."message_resolutions"."message_id" IN ('860e6ad7-b77e-4878-bcc5-3f0cdef02899','f4f2a25b-ab22-43af-8162-2e3d422402ab')
OFFSET '0';

-- 9d. include: chat (~3 ms). Prisma doesn't deduplicate the IDs: one entry per message, not per chat.
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."chats"."id", "public"."chats"."user_id", "public"."chats"."title", "public"."chats"."created_at"
FROM "public"."chats"
WHERE "public"."chats"."id" IN ('d7766486-c374-4c9a-b137-0935036b3c54','d7766486-c374-4c9a-b137-0935036b3c54')
OFFSET '0';

-- 9e. Total count (~68 ms)
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) AS "_count$_all" FROM (
  SELECT "public"."messages"."id" FROM "public"."messages"
  LEFT JOIN "public"."chats" AS "j0" ON ("j0"."id") = ("public"."messages"."chat_id")
  LEFT JOIN "public"."message_resolutions" AS "j1" ON ("j1"."message_id") = ("public"."messages"."id")
  WHERE (("j0"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029' AND ("j0"."id" IS NOT NULL))
     AND (NOT ("j1"."message_id" IS NULL)))
  OFFSET '0'
) AS "sub";
```

What to look for in 9a and 9e:

- **Where the join starts.** It can begin from `chats` filtered by `user_id` (uses `chats_user_id_idx`), go to `messages` by `chat_id`, then to `message_resolutions` by `message_id`. Or it can begin from the whole `message_resolutions` table. The first is better for a user who owns a small share of all data.
- **Whether the planner collapses the double `message_resolutions` join.** The `LEFT JOIN … WHERE j1.message_id IS NOT NULL` behaves like an inner join, and Postgres usually plans it as one. `orderby_1` is still a separate join, joined on the same unique key.
- **The Sort node.** Rows are ordered by `message_resolutions.created_at` after the join, so expect a `Sort` (ideally `top-N heapsort`) over all of the user's resolved messages. An index can't remove this sort unless `message_resolutions` has a `user_id` column (see Observations).

## Observations

- **2a (list chats), 4a/4d (list messages) and 9a/9e (list resolved messages) are the only slow queries.** Everything else is a primary-key or unique-key lookup under ~5 ms.
- **9a has to join, then sort, all of the user's resolved messages to return 20 rows.** If it stays slow after the `chats(user_id)` and `messages(chat_id, created_at)` indexes, consider denormalizing `user_id` onto `message_resolutions` with an index on `(user_id, created_at)`. That turns the page into a single index range scan with no sort.
- **The list queries dominate every interaction.** After each create, delete or resolve, the client refetches the message list (4 queries) and often the chat list (2a) too. So the cost of a click is mostly those reads, not the write.
- **After adding indexes, verify them.** Check that the migration is applied (`\d messages` in psql, or the Indexes tab in DBeaver), run `ANALYZE;`, and re-run 2a, 4a and 4d. Look for `Index Scan` / `Index Scan Backward using messages_chat_id_created_at_idx` instead of `Seq Scan on messages`.
