# SQL queries by user action: after indexes

This file lists the same operations as [2026091301\_\_baseline.md](./2026091301__baseline.md), re-measured after adding indexes and tightening access checks. Each operation includes the exact SQL generated by Prisma, ready to run in DBeaver or psql with `EXPLAIN (ANALYZE, BUFFERS)`, and compares timings with the baseline.

The SQL was captured from the Prisma query log (`logs/prisma-queries.log`, written by `src/prisma/prisma.service.ts`) during two short manual sessions on the same seeded local data: 324 statements in total. Timings are measured by Prisma, so they include driver and network overhead, not only execution time in Postgres. Confirm each improvement with `EXPLAIN (ANALYZE, BUFFERS)`.

> ⚠️ `EXPLAIN ANALYZE` actually executes the statement. Write operations are wrapped in `BEGIN … ROLLBACK` so they leave no data behind.

## What changed

Migration `prisma/migrations/20260914124712_update_notes_tables_add_indexes`:

```sql
CREATE INDEX "chats_user_id_idx" ON "chats"("user_id");
CREATE INDEX "messages_chat_id_created_at_idx" ON "messages"("chat_id", "created_at");
```

An earlier draft also added `message_resolutions_created_at_idx`. It was removed before these sessions, so the numbers below are measured without it.

Application code changes that affect the generated SQL:

- **Message write paths use a new access check.** `resolveMessage`, `unresolveMessage`, `updateTextMessage` and `deleteMessage` now call `MessagesService.checkAccess` instead of `ChatsService.checkAccess`. It's still one query, but it looks up the message and joins its chat (see 3b).
- **`updateChat` and `deleteChat` now call `ChatsService.checkAccess`.** Before, they didn't check ownership at all. Neither was captured in these sessions.

## The sessions

Session 1, in order:

1. Log in and load the current user.
2. Open four chats one after another (2, 1, 6 and 3 unresolved messages).
3. In the 3-message chat: send a message, resolve three messages (two with a note), delete the last one.
4. Create a chat.
5. Send 10 messages in quick succession (~1.4 s) to another chat, growing it from 2 to 12 messages. Each send is followed by a refetch of the message list and the chat list, so their queries interleave in the log.
6. The chat list is refetched 10 more times at the end.

Session 2, in order:

1. Log in again and load the current user.
2. Load the chat list and open the 12-message chat.
3. Open the resolved messages list (13 resolved messages across 3 chats).
4. Open four chats one after another.
5. Open the resolved messages list again.

## 1. Users

| Query | Baseline     | After indexes  |
| ----- | ------------ | -------------- |
| 1a    | not captured | ~15.2, 19.4 ms |

## 2. List chats

`GET /v1/chats` → `ChatsService.listChats`. Two queries in one transaction. Captured 24 times, all first pages (`OFFSET 0`), for a user with 5 chats.

| Query     | Baseline    | After indexes (median)                  | Expected index                                                                    |
| --------- | ----------- | --------------------------------------- | --------------------------------------------------------------------------------- |
| 2a. Page  | ~220–260 ms | ~1.0–4.7 ms (2.1)                       | `chats_user_id_idx`, plus `messages_chat_id_created_at_idx` for `MAX(created_at)` |
| 2b. Count | ~3–5 ms     | ~0.6–2.4 ms (1.3)                       | `chats_user_id_idx`                                                               |
| COMMIT    | —           | ~0.4–1.8 ms (0.7), one sample at 5.5 ms |                                                                                   |
| **Total** | ~225–265 ms | ~2.4–6.7 ms (4.2), one sample at 8.7 ms |                                                                                   |

Before the indexes, the `MAX(created_at)` subquery scanned `messages` once per chat. Now each lookup reads a single entry from the end of `messages_chat_id_created_at_idx`. The query still runs one subquery per chat of the user, so its cost grows with the number of chats. Storing `last_message_at` on `chats` (the TODO in `chats.service.ts`) would remove that.

```sql
-- 2a. Page
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, user_id AS "userId", title, created_at AS "createdAt" FROM chats
WHERE user_id = '9238aa00-e31f-42e3-b0fd-25274f164029'
ORDER BY (
  SELECT MAX(created_at) FROM messages WHERE chat_id = chats.id
) DESC NULLS LAST
LIMIT 20 OFFSET 0;

-- 2b. Total count
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) AS "_count$_all" FROM (
  SELECT "public"."chats"."id" FROM "public"."chats"
  WHERE "public"."chats"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029'
  OFFSET '0'
) AS "sub";
```

Expected plan: `Index Scan using chats_user_id_idx on chats` (or a `Bitmap Heap Scan` on it), with a `SubPlan` made of `Limit → Index Only Scan Backward using messages_chat_id_created_at_idx on messages` with `loops` equal to the number of chats. There should be no `Seq Scan on messages`. With so few chats in the table, the planner may also pick a `Seq Scan on chats`, which is fine at that size.

## 3. Access checks

Access checks are not endpoints. They run first in every request that targets a chat or a message. There are now two of them.

### 3a. Check chat access

`ChatsService.checkAccess`. In these sessions it ran before `listMessages` and `createTextMessage`.

| Query | Baseline    | After indexes (median)                           |
| ----- | ----------- | ------------------------------------------------ |
| 3a    | ~1.4–3.9 ms | ~0.6–3.5 ms (2.1), samples at 6.8 ms and 15.7 ms |

It's a primary-key lookup (`chats_pkey`) with an extra filter on `user_id`, so it isn't affected by the new indexes. Both outliers happened while other requests were in flight: the 15.7 ms sample ran during the burst of message sends, right before a chat list refetch.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."chats"."id", "public"."chats"."user_id", "public"."chats"."title", "public"."chats"."created_at"
FROM "public"."chats"
WHERE ("public"."chats"."id" = '94599d1a-7815-43a0-b898-db139535d03e'
   AND "public"."chats"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029')
LIMIT '1' OFFSET '0';
```

### 3b. Check message access

`MessagesService.checkAccess`. New in this branch. It replaces 3a in `resolveMessage`, `unresolveMessage`, `updateTextMessage` and `deleteMessage`, and also verifies that the message belongs to the chat in the URL.

| Query | Baseline | After indexes (median) |
| ----- | -------- | ---------------------- |
| 3b    | —        | ~2.2–3.1 ms (2.7)      |

The `chat: { userId }` filter becomes a `LEFT JOIN` on `chats`. Both sides are looked up by primary key, so it costs about the same as 3a.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."messages"."id", "public"."messages"."type"::text, "public"."messages"."chat_id", "public"."messages"."created_at"
FROM "public"."messages"
LEFT JOIN "public"."chats" AS "j0" ON ("j0"."id") = ("public"."messages"."chat_id")
WHERE ("public"."messages"."id" = '9aa7d21e-df30-489b-9773-ec08cf244548'
   AND ("public"."messages"."chat_id" = 'd7766486-c374-4c9a-b137-0935036b3c54'
   AND ("j0"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029' AND ("j0"."id" IS NOT NULL))))
LIMIT '1' OFFSET '0';
```

Expected plan: `Limit → Nested Loop` with `Index Scan using messages_pkey on messages` and `Index Scan using chats_pkey on chats j0`.

## 4. List messages in a chat (unresolved filter)

`GET /v1/chats/:chatId/messages?resolution=unresolved` → `MessagesService.listMessages`. After the access check, it runs four queries in one transaction: the page, one per `include` relation (`textMessage`, `messageResolution`), and the count. Captured 25 times across four chats with 1–12 unresolved messages.

| Query                          | Baseline    | After indexes (median)                    | Expected index                                   |
| ------------------------------ | ----------- | ----------------------------------------- | ------------------------------------------------ |
| 4a. Page                       | ~70–125 ms  | ~0.7–5.3 ms (1.6)                         | `messages_chat_id_created_at_idx`                |
| 4b. include: textMessage       | ~1–4 ms     | ~0.6–3.9 ms (1.5), one sample at 8.9 ms   | `text_messages_message_id_key` (unchanged)       |
| 4c. include: messageResolution | ~1–5 ms     | ~1.2–4.7 ms (2.5), one sample at 10.7 ms  | `message_resolutions_message_id_key` (unchanged) |
| 4d. Count                      | ~46–86 ms   | ~0.8–2.6 ms (1.7), one sample at 5.1 ms   | `messages_chat_id_created_at_idx`                |
| COMMIT                         | —           | ~0.6–1.8 ms (0.9), one sample at 3.9 ms   |                                                  |
| **Total**                      | ~130–200 ms | ~5.3–12.7 ms (8.6), one sample at 26.7 ms |                                                  |

4a and 4d are the queries that changed, both ~40–50× faster. There's no visible growth while the chat went from 2 to 12 messages: the list requests for 12 messages took ~7.4–12.7 ms, the first one for 2 messages ~12 ms. The 26.7 ms outlier is a single request in which 4b, 4c and 4d all slowed down together, during the burst of message sends.

**4c is now the slowest of the four queries, and it's useless for this filter.** With `resolution=unresolved`, every returned message has no resolution by definition, so 4c always returns zero rows. It still costs a round trip (median ~2.5 ms, about a third of the request).

```sql
SELECT "public"."messages"."id", "public"."messages"."type"::text, "public"."messages"."chat_id", "public"."messages"."created_at"
FROM "public"."messages"
LEFT JOIN "public"."message_resolutions" AS "j0" ON ("j0"."message_id") = ("public"."messages"."id")
WHERE ("public"."messages"."chat_id" = '94599d1a-7815-43a0-b898-db139535d03e' AND ("j0"."message_id" IS NULL))
ORDER BY "public"."messages"."created_at" DESC
LIMIT '20' OFFSET '0';

-- 4b. include: textMessage

OFFSET '0';

-- 4c. include: messageResolution
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."message_resolutions"."id", "public"."message_resolutions"."message_id", "public"."message_resolutions"."note", "public"."message_resolutions"."created_at"
FROM "public"."message_resolutions"
WHERE "public"."message_resolutions"."message_id" IN ('d8ea136e-7ae8-4779-973a-643919626d25','be256092-e158-461b-8800-6c6b61d31478','dfa3d221-2059-4d87-af59-67f4e3609cd8','b9f4b0ac-15eb-4526-9bab-162e5a441952','408f6797-c6b2-433e-b341-da8eb93edb39','93f5b9ff-13ec-4a80-aaa3-d77be59b061f','1c0c1339-78e1-487b-9058-cd4854923916','6665252c-a305-48ac-8e13-4faa0096eebe','5945ec22-25c3-4aee-8a6f-93b053c9c4ef','b010d16b-34e6-44a5-9fa9-e2bc73ff0ed9','0f4944d8-4b35-49c0-ad42-489c054583c5','1d31a4c5-0ce2-44b6-9eef-7a57e3e33b36')
```

Expected plan for 4a: `Limit → Nested Loop Anti Join`, with `Index Scan Backward using messages_chat_id_created_at_idx on messages` as the outer side and `Index Only Scan using message_resolutions_message_id_key` as the inner side. There should be no `Sort` node and no `Seq Scan on messages`. 4d scans all messages of the chat through the same index, so its cost still grows with chat size.

Captured 11 times, 10 of them within ~1.4 s.

| -------------------------- | ----------- | ---------------------- |
| INSERT messages            | ~3–4.5 ms   | ~1.7–6.1 ms (2.6)      |

## 9. List resolved messages (all chats of the user)

`GET /v1/chats/:chatId/messages/resolved` → `MessagesService.listResolvedMessages`. The route sits under `:chatId`, but the service ignores it: it lists resolved messages across **all** of the user's chats, ordered by resolution date. It doesn't call an access check. It runs five queries in one transaction: the page, one per `include` relation (`textMessage`, `messageResolution`, `chat`), and the count.

Captured twice in session 2, with 13 resolved messages across 3 chats (2 in the baseline).

| Query                          | Baseline | After indexes  |
| ------------------------------ | -------- | -------------- |
| 9a. Page                       | ~127 ms  | ~4.4, 4.5 ms   |
| 9b. include: textMessage       | ~2 ms    | ~2.4, 3.1 ms   |
| 9c. include: messageResolution | ~2.5 ms  | ~3.5, 4.7 ms   |
| 9d. include: chat              | ~3 ms    | ~4.3, 5.6 ms   |
| 9e. Count                      | ~68 ms   | ~2.4, 2.8 ms   |
| COMMIT                         | —        | ~0.8, 1.2 ms   |
| **Total**                      | ~203 ms  | ~17.8, 21.9 ms |

9a improved ~30× and 9e ~25×, with 6× more resolved messages than in the baseline. The request is now ~10× faster overall, less than list chats or list messages, because the three includes have become most of its cost (~10–13 ms of ~18–22 ms).

**9d is the slowest include, and it's mostly redundant.** Prisma doesn't deduplicate the IDs: it sent 13 chat IDs for 3 distinct chats. With three separate include queries, this request would benefit most from `relationLoadStrategy: 'join'`.

```sql
-- 9a. Page
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."messages"."id", "public"."messages"."type"::text, "public"."messages"."chat_id", "public"."messages"."created_at"
```

## Observations

- **The indexes fixed all three slow screens.** List chats went from ~230 ms to a median of ~4 ms, list messages from ~130–200 ms to ~9 ms, and list resolved messages from ~200 ms to ~18–22 ms. Across all 324 statements the median is ~1.7 ms, and only 5 took more than 7 ms: the two cold login lookups and three samples during the message-send burst.
- **Write paths didn't get slower.** With 11 samples, create text message has a median of ~10.5 ms, inside the baseline range. The higher numbers from an earlier run on this branch (22–34 ms for create message from 2 samples, 19.8 ms for create chat) were most likely noise.
- **Two indexes are enough.** `message_resolutions_created_at_idx` was dropped before these sessions, and list resolved messages is still fast: 9a takes ~4.5 ms with 13 resolved messages.
- **The remaining cost is round trips, not execution.** A list messages request is 6 statements (access check, 4 queries, `COMMIT`) at ~1–2.5 ms each, and list resolved messages spends more time in its three includes than in the page and count. Reducing the number of statements would help more than further indexing:
  - Skip the `messageResolution` include when `resolution=unresolved` (4c always returns nothing, ~2.5 ms).
  - Skip the `messageResolution` include in `createTextMessage` (a new message has no resolution, ~1.8 ms).
  - Skip 4b and 4c when 4a returns no rows, or use `relationLoadStrategy: 'join'` to load includes in the page query. That matters most for 9, where 9b–9d take ~10–13 ms.
- **Every write triggers two list refetches.** Each message send was followed by a message list and a chat list request, and the chat list was refetched 10 more times at the end of the session. With ~10 ms per send plus ~12 ms of refetches, the refetches cost more than the write itself. Debouncing them or updating the client cache from the write response would cut the database work per action roughly in half.
- **Outliers come from concurrent requests and cold starts.** During the burst of 10 sends, requests interleave in the log and single queries spike to 9–16 ms. Take the median of several runs rather than a single sample.
- **Growth risks remain.** 2a still runs one `MAX(created_at)` lookup per chat, and 4d and 9e still count every matching row on each page request. 9a still sorts all of the user's resolved messages. They're fast at this data size but grow linearly. Storing `last_message_at` on `chats`, denormalizing `user_id` onto `message_resolutions` with an index on `(user_id, created_at)`, cursor pagination, and dropping or caching `totalSize` would address these if they become slow again.
