# SQL queries by user action: after indexes

This file lists the same operations as [2026091301\_\_baseline.md](./2026091301__baseline.md), re-measured after adding indexes and tightening access checks. Each operation includes the exact SQL generated by Prisma, ready to run in DBeaver or psql with `EXPLAIN (ANALYZE, BUFFERS)`, and compares timings with the baseline.

The SQL was captured from the Prisma query log (see `src/prisma/prisma.service.ts`) during a manual session on the same seeded local data. Timings are measured by Prisma, so they include driver and network overhead, not only execution time in Postgres. Confirm each improvement with `EXPLAIN (ANALYZE, BUFFERS)`.

> ⚠️ `EXPLAIN ANALYZE` actually executes the statement. Write operations are wrapped in `BEGIN … ROLLBACK` so they leave no data behind.

## What changed

Migration `prisma/migrations/20260914124712_update_notes_tables_add_indexes`:

```sql
CREATE INDEX "chats_user_id_idx" ON "chats"("user_id");
CREATE INDEX "messages_chat_id_created_at_idx" ON "messages"("chat_id", "created_at");
```

An earlier draft also added `message_resolutions_created_at_idx`. It was removed before this session, so the numbers below are measured without it.

Application code changes that affect the generated SQL:

- **Message write paths use a new access check.** `resolveMessage`, `unresolveMessage`, `updateTextMessage` and `deleteMessage` now call `MessagesService.checkAccess` instead of `ChatsService.checkAccess`. It's still one query, but it looks up the message and joins its chat (see 3b).
- **`updateChat` and `deleteChat` now call `ChatsService.checkAccess`.** Before, they didn't check ownership at all. Neither was captured in this session.0

## 1. Load current user

`GET /v1/auth/me` and `POST /v1/auth/refresh` both call `UsersService.findById` and produce identical SQL. **Not captured in this session.** It's a primary-key lookup, so the indexes don't affect it.

```sql
FROM "public"."users"
WHERE ("public"."users"."id" = '9238aa00-e31f-42e3-b0fd-25274f164029' AND 1=1)
LIMIT '1' OFFSET '0';
```

## 2. List chats

`GET /v1/chats` → `ChatsService.listChats`. Two queries in one transaction. Captured 4 times, after creating a chat, sending two messages and deleting a message.

| Query     | Baseline    | After indexes | Expected index                                                                    |
| --------- | ----------- | ------------- | --------------------------------------------------------------------------------- |
| 2a. Page  | ~220–260 ms | ~1.2–4.5 ms   | `chats_user_id_idx`, plus `messages_chat_id_created_at_idx` for `MAX(created_at)` |
| 2b. Count | ~3–5 ms     | ~0.8–2.6 ms   | `chats_user_id_idx`                                                               |
| COMMIT    | —           | ~0.5–0.8 ms   |                                                                                   |

Before the indexes, the `MAX(created_at)` subquery scanned `messages` once per chat. Now each lookup reads a single entry from the end of `messages_chat_id_created_at_idx`. The query still runs one subquery per chat of the user, so its cost grows with the number of chats. Storing `last_message_at` on `chats` (the TODO in `chats.service.ts`) would remove that.

```sql
-- 2a. Page
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, user_id AS "userId", title, created_at AS "createdAt" FROM chats
WHERE user_id = '9238aa00-e31f-42e3-b0fd-25274f164029'
ORDER BY (
  SELECT MAX(created_at) FROM messages WHERE chat_id = chats.id
) DESC NULLS LAST
LIMIT 20 OFFSET 0;

-- 2b. Total count
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) AS "_count$_all" FROM (
  SELECT "public"."chats"."id" FROM "public"."chats"
  WHERE "public"."chats"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029'
  OFFSET '0'
) AS "sub";
```

Expected plan: `Index Scan using chats_user_id_idx on chats` (or a `Bitmap Heap Scan` on it), with a `SubPlan` made of `Limit → Index Only Scan Backward using messages_chat_id_created_at_idx on messages` with `loops` equal to the number of chats. There should be no `Seq Scan on messages`.

## 3. Access checks

Access checks are not endpoints. They run first in every request that targets a chat or a message. There are now two of them.

### 3a. Check chat access

`ChatsService.checkAccess`. In this session it ran before `listMessages` and `createTextMessage`.

| Query | Baseline    | After indexes                    |
| ----- | ----------- | -------------------------------- |
| 3a    | ~1.4–3.9 ms | ~1.1–2.9 ms (samples at 4.0–4.3) |

It's a primary-key lookup (`chats_pkey`) with an extra filter on `user_id`, so it isn't affected by the new indexes. The differences are noise.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."chats"."id", "public"."chats"."user_id", "public"."chats"."title", "public"."chats"."created_at"
FROM "public"."chats"
WHERE ("public"."chats"."id" = 'd7766486-c374-4c9a-b137-0935036b3c54'
   AND "public"."chats"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029')
LIMIT '1' OFFSET '0';
```

### 3b. Check message access

`MessagesService.checkAccess`. New in this branch. It replaces 3a in `resolveMessage`, `unresolveMessage`, `updateTextMessage` and `deleteMessage`, and also verifies that the message belongs to the chat in the URL.

| Query | Baseline | After indexes                 |
| ----- | -------- | ----------------------------- |
| 3b    | —        | ~1.6, 3.1, 4.2 ms (3 samples) |

The `chat: { userId }` filter becomes a `LEFT JOIN` on `chats`. Both sides are looked up by primary key, so it should cost about the same as 3a.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."messages"."id", "public"."messages"."type"::text, "public"."messages"."chat_id", "public"."messages"."created_at"
FROM "public"."messages"
LEFT JOIN "public"."chats" AS "j0" ON ("j0"."id") = ("public"."messages"."chat_id")
WHERE ("public"."messages"."id" = '9aa7d21e-df30-489b-9773-ec08cf244548'
   AND ("public"."messages"."chat_id" = 'd7766486-c374-4c9a-b137-0935036b3c54'
   AND ("j0"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029' AND ("j0"."id" IS NOT NULL))))
LIMIT '1' OFFSET '0';
```

Expected plan: `Limit → Nested Loop` with `Index Scan using messages_pkey on messages` and `Index Scan using chats_pkey on chats j0`.

## 4. List messages in a chat (unresolved filter)

`GET /v1/chats/:chatId/messages?resolution=unresolved` → `MessagesService.listMessages`. After the access check, it runs four queries in one transaction: the page, one per `include` relation (`textMessage`, `messageResolution`), and the count. Captured 14 times across three chats with 0–9 unresolved messages.

| Query                          | Baseline    | After indexes                   | Expected index                                   |
| ------------------------------ | ----------- | ------------------------------- | ------------------------------------------------ |
| 4a. Page                       | ~70–125 ms  | ~1.0–3.2 ms                     | `messages_chat_id_created_at_idx`                |
| 4b. include: textMessage       | ~1–4 ms     | ~1.0–4.6 ms (one sample at 5.9) | `text_messages_message_id_key` (unchanged)       |
| 4c. include: messageResolution | ~1–5 ms     | ~1.5–5.6 ms (one sample at 8.8) | `message_resolutions_message_id_key` (unchanged) |
| 4d. Count                      | ~46–86 ms   | ~0.8–3.2 ms (one sample at 7.5) | `messages_chat_id_created_at_idx`                |
| COMMIT                         | —           | ~0.5–4.3 ms                     |                                                  |
| **Total**                      | ~130–200 ms | ~6–18 ms                        |                                                  |

4a and 4d are the queries that changed, both ~40× faster. 4b and 4c were already using unique-key indexes, and their spread is noise. They're now the largest part of the request, together with `COMMIT`.

```sql
-- 4a. Page
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."messages"."id", "public"."messages"."type"::text, "public"."messages"."chat_id", "public"."messages"."created_at"
FROM "public"."messages"
LEFT JOIN "public"."message_resolutions" AS "j0" ON ("j0"."message_id") = ("public"."messages"."id")
WHERE ("public"."messages"."chat_id" = 'd7766486-c374-4c9a-b137-0935036b3c54' AND ("j0"."message_id" IS NULL))
ORDER BY "public"."messages"."created_at" DESC
LIMIT '20' OFFSET '0';

-- 4b. include: textMessage
EXPLAIN (ANALYZE, BUFFERS)

FROM "public"."text_messages"
WHERE "public"."text_messages"."message_id" IN ('85ef504c-df8d-4379-98bb-80ad8c44575f','6d0d777c-4c33-4d7e-9152-0ac596ac590c','97352bf4-b5c6-4d6d-b76e-845927e3f55c','9aa7d21e-df30-489b-9773-ec08cf244548','311538f3-340d-4c55-8454-9c4cd454d7c6','427a73ca-1c25-4970-a3f9-c19c32e23fc5','1d65c541-d1a3-4564-afc5-6db6c469dc97','b40ae7f6-a752-4e40-acc1-84fa1c79bb78','dcd6569d-8076-4d2f-94f9-a69442201dcd')
OFFSET '0';

-- 4c. include: messageResolution
EXPLAIN (ANALYZE, BUFFERS)
SELECT "public"."message_resolutions"."id", "public"."message_resolutions"."message_id", "public"."message_resolutions"."note", "public"."message_resolutions"."created_at"
FROM "public"."message_resolutions"
WHERE "public"."message_resolutions"."message_id" IN ('85ef504c-df8d-4379-98bb-80ad8c44575f','6d0d777c-4c33-4d7e-9152-0ac596ac590c','97352bf4-b5c6-4d6d-b76e-845927e3f55c','9aa7d21e-df30-489b-9773-ec08cf244548','311538f3-340d-4c55-8454-9c4cd454d7c6','427a73ca-1c25-4970-a3f9-c19c32e23fc5','1d65c541-d1a3-4564-afc5-6db6c469dc97','b40ae7f6-a752-4e40-acc1-84fa1c79bb78','dcd6569d-8076-4d2f-94f9-a69442201dcd')
OFFSET '0';

-- 4d. Total count
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) AS "_count$_all" FROM (
  SELECT "public"."messages"."id" FROM "public"."messages"
  LEFT JOIN "public"."message_resolutions" AS "j0" ON ("j0"."message_id") = ("public"."messages"."id")
  WHERE ("public"."messages"."chat_id" = 'd7766486-c374-4c9a-b137-0935036b3c54' AND ("j0"."message_id" IS NULL))
  OFFSET '0'

```

Expected plan for 4a: `Limit → Nested Loop Anti Join`, with `Index Scan Backward using messages_chat_id_created_at_idx on messages` as the outer side and `Index Only Scan using message_resolutions_message_id_key` as the inner side. There should be no `Sort` node and no `Seq Scan on messages`. 4d scans all messages of the chat through the same index, so its cost still grows with chat size.

For an empty chat, 4b and 4c become `IN (NULL)` and still run (~1.8 and ~3.6 ms in this session). They return nothing, but they're a round trip each.

## 5. Create text message

`POST /v1/chats/:chatId/messages/text` → `MessagesService.createTextMessage`. After the access check, it runs five queries in one transaction: Prisma inserts the rows, then re-reads the message with its `include` in three SELECTs by primary or unique key. Captured twice, both in the newly created chat.

| Query                               | Baseline       | After indexes    |
| ----------------------------------- | -------------- | ---------------- |
| INSERT messages                     | ~3–4.5 ms      | ~4.5–4.8 ms      |
| INSERT text_messages                | ~2.7–5.5 ms    | ~4.8–5.0 ms      |
| SELECT messages / text / resolution | ~1–8.5 ms each | ~1.9–7.7 ms each |
| COMMIT                              | —              | ~1.5–1.7 ms      |
| **Total**                           | ~10–20 ms      | ~22 and ~34 ms   |

The total is higher than the baseline, but every query is within its baseline range, just at the upper end. The three SELECTs by primary or unique key can't be affected by the new indexes, and they slowed down as much as the inserts, so this looks like noise rather than index maintenance cost. `messages_chat_id_created_at_idx` adds one B-tree insert per message, which should cost microseconds. With two samples, re-measure before drawing conclusions.

## 9. List resolved messages (all chats of the user)

`GET /v1/chats/:chatId/messages/resolved` → `MessagesService.listResolvedMessages`. The route sits under `:chatId`, but the service ignores it: it lists resolved messages across **all** of the user's chats, ordered by resolution date. It doesn't call an access check. It runs five queries in one transaction: the page, one per `include` relation (`textMessage`, `messageResolution`, `chat`), and the count. The user had 6 resolved messages at that point (2 in the baseline).

| Query                          | Baseline | After indexes |
| ------------------------------ | -------- | ------------- |
| 9a. Page                       | ~127 ms  | ~2.7 ms       |
| 9b. include: textMessage       | ~2 ms    | ~2.1 ms       |
| 9c. include: messageResolution | ~2.5 ms  | ~3.1 ms       |
| 9d. include: chat              | ~3 ms    | ~4.2 ms       |
| 9e. Count                      | ~68 ms   | ~3.4 ms       |
| COMMIT                         | —        | ~1.4 ms       |
| **Total**                      | ~203 ms  | ~17 ms        |

9a improved ~45× and 9e ~20×, with 3× more resolved messages than in the baseline. There's one sample in each session, so treat the numbers as rough. 9b–9d are primary-key or unique-key lookups and weren't affected. In 9d, Prisma sent the same chat ID 6 times.

This was measured **without** `message_resolutions_created_at_idx`, which confirms that `chats_user_id_idx` and `messages_chat_id_created_at_idx` alone explain the speedup, and that dropping the resolutions index was safe.

```sql

FROM "public"."messages"
LEFT JOIN "public"."message_resolutions" AS "orderby_1" ON ("orderby_1"."message_id") = ("public"."messages"."id")
LEFT JOIN "public"."chats" AS "j0" ON ("j0"."id") = ("public"."messages"."chat_id")
LEFT JOIN "public"."message_resolutions" AS "j1" ON ("j1"."message_id") = ("public"."messages"."id")
WHERE (("j0"."user_id" = '9238aa00-e31f-42e3-b0fd-25274f164029' AND ("j0"."id" IS NOT NULL))
   AND (NOT ("j1"."message_id" IS NULL)))
ORDER BY "orderby_1"."created_at" DESC
LIMIT '20' OFFSET '0';

-- 9b. include: textMessage
EXPLAIN (ANALYZE, BUFFERS)
```

What to look for in 9a and 9e:

- **Where the join starts.** Expect it to start from `chats_user_id_idx`, go to `messages` through `messages_chat_id_created_at_idx` (by `chat_id` prefix), then join `message_resolutions` through `message_resolutions_message_id_key`.
- **The Sort node.** Rows are ordered by `message_resolutions.created_at` after the join, so expect a `Sort` (ideally `top-N heapsort`) over all of the user's resolved messages. Its cost grows with that number.

## Observations

- **The indexes fixed all three slow screens.** List chats went from ~230 ms to ~3–8 ms, list messages from ~130–200 ms to ~6–18 ms, and list resolved messages from ~200 ms to ~17 ms. No read query is consistently above ~5 ms anymore.
- **Two indexes are enough.** `message_resolutions_created_at_idx` was dropped before this session, and list resolved messages is still fast.
- **The remaining cost is round trips, not execution.** A list messages request is now 6 statements (access check, 4 queries, `COMMIT`) at ~1–4 ms each. Reducing the number of statements would help more than further indexing: for example, skipping 4b and 4c when 4a returns no rows, or using `relationLoadStrategy: 'join'` to load includes in the page query.
- **Write paths didn't get measurably slower.** Create text message and create chat look slower, but the samples are few and even the primary-key SELECTs in the same requests slowed down, which points to noise. Re-measure with `EXPLAIN (ANALYZE, BUFFERS)`.
- **Outliers come from concurrent requests and idle gaps.** The client refetches the chat list and the message list at the same time after a write, and their queries interleave in the log. Take the median of several runs rather than a single sample.
- **The pg driver warns about overlapping queries.** During list resolved messages, Node logged `DeprecationWarning: Calling client.query() when the client is already executing a query`. It means two queries were sent on the same `pg` client at once. It's harmless in the current version but will fail in `pg@9`, so check how the Prisma adapter runs `$transaction([...])` queries before upgrading.
- **Growth risks remain.** 2a still runs one `MAX(created_at)` lookup per chat, and 4d and 9e still count every matching row on each page request. 9a still sorts all of the user's resolved messages. They're fast at this data size but grow linearly. Storing `last_message_at` on `chats`, denormalizing `user_id` onto `message_resolutions` with an index on `(user_id, created_at)`, cursor pagination, and dropping or caching `totalSize` would address these if they become slow again.
